# 全体像の HTML の書き方

データ基盤の全体像の HTML（HTML 1ファイル）の書き方。回答から作った例であることが読み手に分かるようにする。読み手は組織の中の人で、構築をどの会社や部署が担当するかは決めない。

ページの枠・CSS・8節の見出しと「このページの使い方」の文は `templates/overview-page.html` にある。テンプレートの `{{...}}` だけを置き換え、CSS と見出しは変えない。

## 節の構成

次の8節をこの順に置く。「このページの使い方」はテンプレートに書いてあるので、内容を作らない。

| 節                   | 載せるもの                                                                   | 使うもの                          |
| -------------------- | ---------------------------------------------------------------------------- | --------------------------------- |
| このページの使い方   | 読む人ごとに見る節と挙げること                                               | テンプレートの固定の文            |
| 前提にした回答       | 構成と画面を決めるのに使った回答の要約                                       | 要件シートの回答                  |
| 画面のイメージ       | 数値のタイル・グラフ・AI チャットの画面                                      | Q1-1・Q1-3・Q1-5・Q2 の主なデータ |
| 構成のイメージ       | 構成図                                                                       | 構成の推奨案                      |
| テーブルの構成       | テーブルの関係図、テーブルごとの更新の方法と理由、ロールごとに読めるテーブル | テーブルの構成・Q1-2・Q4-3・Q4-4  |
| この構成を選んだ理由 | 決めたこと・選んだもの・選んだ理由・選ばなかった案の表と出典                 | 構成の推奨案と代替案              |
| 進め方と期間の例     | 工程ごとの担当と週単位の期間を描いたガントチャート                           | テーブルの構成・次にやること      |
| 次にやること         | 最初にやることを順番に並べた表                                               | 決まっていないことの一覧          |

## 前提にした回答

- 構成・テーブル・画面を決めるのに使った回答を、5〜8 行の箇条書きにする。読む人が前提の誤りに気づけるようにするため
- 1 行に 1 つの事柄を、回答の中身で書く（例: 見る人は営業企画部と店舗の責任者の 50 名、毎週月曜に見る / 鮮度は前日までで足りる / 外部からの接続制限がある）
- Q 番号は書かない。空欄と「不明」の項目はここに書かず、次にやることに回す

## 画面のイメージ

- Q1-5 から取った解消する課題を 1 文で書く。「ダミーデータです」の表示はテンプレートに入っている
- Q1-1 の判断に使う数値を2〜3個のタイルにし、その下にグラフを置く。グラフの種類は Q1-1 と Q1-3 から決める
- グラフはページの中に SVG で描く。グラフを描くために、ほかの skill を読み込まない
- 色はテンプレートの CSS 変数（`--series-1`・`--series-2`・`--neg`）を使う。点や棒に `class="hit"` と `data-tip` を付けると、カーソルを合わせたときに値が出る。グラフの下に、数値を見られる表を `<details>` で置く
- 列名は Q1-1 に出てくる指標と軸と Q2 の主なデータから、一般的な名前で作る。各グラフの下に1行の単位と集計方法を書く
- Q1-3 で「AI チャット」が選ばれていたら、Q1-1 から作った質問の例とダミーの回答（文章と表）を載せる
- タイル・グラフ・AI チャットの数値は同じダミーデータから計算し、合計や率が互いに合うようにする

## 構成のイメージ

- 構成図には構成で決めた具体的なサービスをすべて描く。データの取り出し・起動の仕組み・秘密情報の保管・接続の権限・データの層・ウェアハウス・AI チャットの機能まで描き、「取り込み」のような抽象的な箱で済ませない
- 構成図は draw.io 公式の drawio skill で `.drawio` を作り、draw.io Desktop の CLI で PNG に書き出す。HTML や SVG を手で組んで描かない
- AWS は draw.io に入っている `mxgraph.aws4` のアイコンを、Google Cloud は `mxgraph.gcp2` のアイコンを使う。Snowflake・dbt・BI ツールなど draw.io にアイコンがない製品は、ロゴの画像を外から取ってきて埋め込まない。draw.io に入っている製品に依存しない線のアイコンで役割ごとに描き分け、ラベルに製品名と役割を書く。線の色は水色（`strokeColor=#29B5E8;fillColor=none;strokeWidth=2`）にそろえる
  - テーブル・データの層は円柱（`shape=cylinder3`）
  - ステージ・ファイルは `shape=mxgraph.ios7.icons.documents`
  - タスク・Snowpipe など時刻やイベントで動く処理は `shape=mxgraph.ios7.icons.clock`
  - dbt など変換の処理は `shape=mxgraph.ios7.icons.settings`
  - 画面は `shape=mxgraph.ios7.icons.monitor`
  - AI チャットは `shape=mxgraph.aws4.chat`（`fillColor=#29B5E8;strokeColor=none`）
  - 利用者は `shape=mxgraph.aws4.users`
  - ウェアハウスやポリシーのように一覧に当てはまらないものは、四角の枠に名前を書く
- `.drawio` は全体像の HTML と同じ場所に置く。PNG は base64 でページに埋め込み、1ファイルで送れるようにする。構成図は縮小せず実寸の幅で表示し、横にスクロールして見られるようにする
- 書き出した PNG を開き、線がラベルの文字の上を通っていないか、文字が枠からはみ出していないかを確かめる
- 構成図は左から Q2 のソース・取り出しと保存・変換・画面と AI チャット・Q1-2 の見る人の順に並べる
- 置き場所が決まっていないデータは点線の枠で描き、「確認中」と書く

## テーブルの構成

- 関係図はページの中に SVG で描く。draw.io は使わない
- 左から RAW・STAGING・MART の 3 列に並べ、1 テーブルを 1 つの箱にする。箱にはテーブル名と、何のデータかを 1 行で書く
- 元のテーブルから作るテーブルへ矢印を引く。MART で結合するときは、結合に使う列（店舗コードなど）を矢印の近くに書く
- 試行で作るテーブルは実線、試行のあとに作るテーブルは点線の箱にする
- 箱の線と文字の色はテンプレートの CSS 変数を使う。箱の文字が箱からはみ出さない幅にする
- 図の下に、テーブルごとの更新の方法と理由の表を置く。列はテーブル・更新の方法・理由にする
  - RAW のテーブルがすべて追記なら、RAW は 1 行にまとめ、「RAW はすべて追記」と理由を 1 つだけ書く
  - 更新の方法は「追記（INSERT）」「差分の反映（MERGE）」「洗い替え」のどれかで書く。決められないものは「未定」にする
  - 理由には、その方法を選んだ根拠を回答の中身で書く（例: 元のシステムが変わった分だけを出力するため、差分の反映にする）
  - 未定のものは、何が分かればどちらに決まるかを書く（例: 毎回すべてを出すなら洗い替え、変わった分だけなら差分の反映）
- 更新の方法の表の下に、ロールごとに読めるテーブルの表を置く。列はロール・誰・読めるテーブル・できることにし、4〜6 行に収める
  - 閲覧のロールは Q1-2 の部署ごとに分ける。開発のロール（Q4-3 で決めた作り方で変換を作る人）と、取り込み用のサービスユーザーのロールを足す
  - 読めるテーブルには層と範囲を書く（例: MART の全店舗、RAW への書き込み）。Q4-4 で個人情報を含むなら、個人情報の列を見られるロールを書く
  - 部署ごとに見せる行を絞るか（例: 店舗の責任者は自分の店舗だけを見るか）のように回答から決まらない点は「未定」と書き、決める方法を次にやることに回す

## この構成を選んだ理由

- 判断が分かれた構成要素ごとに 1 行を作り、選んだ理由と選ばなかった案を書く。行は多くても 8 行にする
- セキュリティの対策（個人情報の列を隠す・接続元を限るなど）は、まとめて 1 行にする。ロールの分け方はテーブルの構成の節に書くので、この行では使う機能の名前だけを書く
- 公式ドキュメントで確かめられなかったこと（提供状況など）は理由の表に書かず、データ基盤の担当が確かめることとして次にやることに入れる
- ページに Q 番号を書かない。読み手は Q 番号がどの質問かを知らないため、根拠は「利用中のクラウドが AWS のため」のように回答の中身で書く。設計の指針に照らした判断と、公式ドキュメントで確かめた製品の制約（エディションの要件など）もここに書く
- 選ばなかった案には、その案が向く条件を 1 文で書く。選ばなかった案には出典を付けない
- 表の下に、選んだ構成の制約を確かめた公式ドキュメントだけを出典として並べ、確認日を添える
- 試行のあとに本番へ広げる手順は書かない。進め方と期間の例と次にやることに含まれるため

## 進め方と期間の例

- ガントチャートは draw.io を使わず、HTML の表で描く。表のクラスは `gantt` にし、1 行が 1 工程、列が工程・担当・週になる。棒は工程の期間の週のセルを colspan で 1 つにつなぎ、そのセルに `<div class="bar biz">`（データを使う部署）・`data`（データ基盤の担当）・`it`（情報システム部門）を置き、試行のあとの工程には `later` を足して点線にする
- 工程は「要件の確認 → 設計 → 開発 → テスト → 試行と評価 → 本番への展開」の順に並べる
- 開発はデータのソースや作るもの（取り込み・変換・画面と AI チャット）ごとに行を分けてよい。分けた行は「開発（取り込み）」のように名前の先頭を「開発」にする
- テストは開発のあと、試行の前に置く。テストの担当はデータ基盤の担当、受け入れの確認の担当はデータを使う部署にする
- 最初は Q1-1 に必要なデータだけで小さく試す工程を並べ、試行のあとの工程を点線で描く
- 各工程の担当は役割で書く（データを使う部署・データ基盤の担当・情報システム部門）。会社名や「貴社・弊社」は書かない
- 期間は例であり、決まっていないことが決まると変わることを書く

## 次にやること

- 決まっていないことの一覧を、最初にやる順に並べた表にする。列は順番・やること・決める人・決まると進められる工程にする
- やることは「予算・目標のファイルの置き場所と更新日を決める」のように、誰が何を決めるかが分かる文にする
- 決める人は役割で書く（データを使う部署・データ基盤の担当・情報システム部門）
- 進め方と期間の例の最初の工程に要るものを上に置く
- 「取り込みや変換が失敗したときに通知を受けて直す人を決める」を必ず入れる。決める人は情報システム部門にする

## 書かないもの

- 実際の数値・取引先名・個人名
- 費用の金額
